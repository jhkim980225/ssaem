# 법령 참고자료 (공용 RAG)

현행 세법 조문을 **전 강사 공용 참고자료**로 깔아 두고, 답변에서 강사 자료와 함께 근거로
쓴다. 왜 필요한가 — 세법은 해마다 바뀌는데 **기출 해설은 출제 당시 법**이고 **모델 지식은
학습 시점**에 멈춰 있다. "지금 기준으로 얼마인가"에 답하려면 현행 조문이 있어야 한다.

## 데이터

| | |
|---|---|
| 출처 | 국가법령정보센터 오픈API (`law.go.kr/DRF`) — 조문 단위 JSON |
| 담는 것 | 조문 원문 그대로 (요약하지 않는다) |
| 현재 적재 | 소득세법 · 소득세법 시행령 (현행, 2026.07.01. 시행) |

요약본을 만들지 않는 이유: 숫자를 옮겨 적다 틀리면 손해가 더 크고, 출처에 조문 번호가
그대로 찍혀 학생이 원문을 확인할 수 있다.

## 저장 구조

별도 테이블을 두지 않고 **`documents`/`chunks`의 `teacher_id IS NULL` = 공용**으로 쓴다
(마이그레이션 `20260921010000_law_reference.sql`).

- **왜 별도 테이블이 아닌가**: `message_citations.chunk_id`가 `chunks(id)`를 참조한다 —
  법령을 다른 테이블에 두면 근거(출처) 기록이 통째로 끊긴다.
- **왜 시스템 강사 계정이 아닌가**: `profiles`에 강사 행을 만들면 학생의 강사 선택
  목록에 뜬다.
- 강사 자료 조회는 전부 `eq("teacher_id", uid)`라 공용 행이 섞여 들어가지 않는다.
  다만 **필터 없이 세는 곳**(랜딩 통계·`/dev` 지표)은 `not("teacher_id","is",null)`로
  빼야 한다 — 법령 문서는 "강사가 올린 자료"가 아니다.

## 검색 — 왜 따로 부르는가

`match_chunks`(강사 것만)와 `match_reference_chunks`(공용)를 **각각** 부르고,
`src/lib/retrieve.ts`가 법령을 정해진 몫(`LAW_K=2`)만 뒤에 붙인다.

한 쿼리에서 섞으면 소득세 질문 하나에 조문이 상위 k개를 다 차지해 **정작 그 선생님
자료가 밀려난다**. 법령은 보조 근거이지 강사 자료의 대체재가 아니다.

임베딩이 안 될 때(키 없음·쿼터)의 lexical 폴백에는 법령을 **넣지 않는다** — 청크가 수백
개라 키워드 랭킹을 뒤덮는다.

## 유사도 임계값 (`LAW_MIN_SIM`)

한국어 임베딩은 **바닥 유사도가 높다**. 무관한 질문("AES랑 RSA 차이")도 0.5대가 나오므로
값을 감으로 잡으면 안 된다. 질문 33개로 실측한 분포:

| 질문 종류 | min | 중앙 | max |
|---|---|---|---|
| 세법 14개 | 0.690 | 0.768 | 0.799 |
| 회계 15개 | 0.579 | 0.648 | 0.741 |
| 무관 4개 | 0.509 | 0.558 | 0.561 |

| 임계값 | 세법 포함 | 회계 오포함 | 무관 오포함 |
|---|---|---|---|
| 0.65 | 14/14 | 7/15 | 0/4 |
| **0.68** | **14/14** | **6/15** | **0/4** |
| 0.70 | 12/14 | 3/15 | 0/4 |
| 0.74 | 10/14 | 1/15 | 0/4 |

세법과 회계가 0.69~0.74 구간에서 겹친다 — 깔끔히 안 갈린다. **세법 질문을 놓치는 쪽이 더
나쁘므로 재현율을 택해 0.68**로 뒀다. 딸려오는 회계 질문은 대부분 "감가상각·재고자산
평가"처럼 세법에도 같은 주제가 있는 경우라, 프롬프트에서 *"무관하면 언급하지 마라"*로
비용을 토큰만으로 묶는다. (실측: 감가상각 질문에 시행령 제66조가 붙어도 답변은 기업회계
정액법만 설명한다.)

## 프롬프트 (`src/lib/prompt.ts`)

강사 자료와 법령을 **섹션을 나눠** 넣는다. 섞으면 모델이 조문을 "선생님이 올린 자료"로
소개하고, 출제 당시 기준과 현행 기준을 구분하지 못한다. 지시 4줄:

1. 세법 수치는 조문을 우선 근거로 삼고 어느 조문인지 밝혀라
2. **기출 해설과 다르면 '출제 당시 기준' / '현행 기준'으로 나눠 설명하라** — 안 넣으면
   학생이 해설과 답변이 어긋나는 이유를 알 수 없다
3. 조문에 없는 수치는 확정적으로 말하지 말고 확인이 필요하다고 덧붙여라
4. 질문과 무관하면 아예 언급하지 마라 (기업회계 질문에 세법을 섞지 마라)

## 적재·검증

```bash
npx tsx scripts/import-law.ts                      # 소득세법 + 시행령
npx tsx scripts/import-law.ts "부가가치세법" "부가가치세법 시행령"
npx tsx scripts/verify-law.ts                      # 적재·조문검색·프롬프트 검증
```

- **재실행 안전**: 시행일과 **본문**이 모두 같으면 건너뛴다. 본문까지 비교하는 이유 —
  파서(`clean`/청킹)를 고치면 시행일이 같아도 내용이 달라지는데, 개수만 보면 옛 텍스트가
  그대로 남는다.
- **무중단 교체**: 달라졌으면 `kind='law_draft'` 문서에 채우고 **다 채운 뒤에** `'law'`로
  바꾸며 옛 문서를 지운다. draft는 검색에서 빠진다. 먼저 지우면 채우는 20~30분 동안
  답변 근거가 통째로 비는 시간이 생긴다 (2026-09-21에 실제로 겪었다).
- **이어받기는 ord 기준**: 이미 들어간 `ord`를 읽어 빠진 자리만 채운다. 개수로 세면 앞
  실행이 아직 살아 있을 때 같은 청크가 두 벌 들어간다 — 실제로 38행이 중복됐다.
  `chunks(document_id, ord)` 유니크 인덱스로 한 번 더 막는다.
- **임베딩 한도 두 가지** (Gemini 무료 티어):
  - *요청당*: 429는 요청 건수가 아니라 **한 요청에 담긴 글자수**에 걸린다 (실측: 1,600자
    청크 8건 14,680자 통과 / 10건 18,350자 실패). 글자수 12,000자로 묶는다.
  - *하루*: `EmbedContentRequestsPerDayPerUserPerProjectPerModel-FreeTier = 1000`.
    법령 하나가 200~400청크라 **하루에 두세 번 전량 재적재하면 쿼터가 바닥난다.**
    소진되면 스크립트가 그 사실을 알리고 멈춘다 — 다음 날 같은 명령이면 이어서 채운다.
  - 전량 적재에 20~30분 걸린다.
- **OC**: 기본값 `test`로 동작한다. 막히면 law.go.kr에서 본인 OC를 발급받아
  `LAW_OC=<id>`로 넘긴다.

## 원문 가공에서 주의할 것

법령 API 본문은 표를 **`<img>`로 감싼 괘선 아트**로 준다. 그대로 넣으면 임베딩도 화면도
못 쓴다. `clean()`이:

1. `<img>` 태그만 벗기고 **안쪽 표 텍스트는 살린다**
2. 테두리 줄(`┌─┬┐`)은 버리고 `│`로 칸을 갈라 `셀 | 셀`로 편다
3. **한 칸이 두 줄로 조판된 행을 앞 행에 합친다** — 세율표의 "1,400만원 초과 / 5,000만원
   이하"가 여기 해당한다. 안 합치면 표가 쪼개져 학생이 구간을 읽을 수 없다

## 한계

- 지금은 **소득세법 계열만** 있다. 부가가치세법·법인세법 질문에도 임계값을 넘으면
  소득세법 조문이 붙을 수 있다 (예: "세금계산서 발급 기한" → 소득세법 제163조 계산서).
  해당 법을 같이 적재하면 해소된다.
- 시행규칙·별표(세액표 등)는 아직 안 담았다.
- 법이 개정되면 **다시 돌려야 한다** — 자동 갱신은 없다.
- **2026-09-21 현재 소득세법 시행령은 355청크 중 10개만 들어가 있다**(`law_draft`,
  검색 제외). 표 파싱을 고쳐 재적재하던 중 임베딩 일일 쿼터가 소진됐다. 쿼터가 돌아온 뒤
  `npx tsx scripts/import-law.ts` 한 번이면 이어서 채워진다.
