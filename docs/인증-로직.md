# 로그인 · 회원가입 로직

코드 실측 기준 (2026-08-09). 관련 파일: `src/lib/auth.ts`, `src/lib/account.ts`, `src/lib/role.ts`, `src/app/login/page.tsx`, `src/app/api/signup/route.ts`.

## 한눈에

- 인증은 **Supabase Auth**(이메일+비밀번호). 세션 쿠키가 아니라 클라이언트가 `access_token`을 `Authorization: Bearer`로 보낸다.
- 로그인 화면은 **`/login` 하나**. 역할 탭(학생/강사) × 모드(로그인/회원가입) 조합으로 동작한다.
- 서버는 전부 `serviceClient()`(service role, RLS 우회)를 쓴다 → **모든 접근 제어가 앱 코드 책임**이다. RLS는 2차 방어선일 뿐.
- 역할은 `profiles.role` (`teacher` / `student` / `admin`)이 유일한 진실. 클라이언트가 보낸 값은 신뢰하지 않는다.

## 아이디 로그인 (이메일 없이)

학생이 이메일을 안 갖고 있어도 쓸 수 있게, 아이디를 내부 이메일로 매핑한다. `src/lib/account.ts`:

```
toEmail("test")      → "test@ssaem.kr"     // @ 없으면 아이디로 취급
toEmail("a@b.com")   → "a@b.com"           // @ 있으면 이메일 그대로
```

- 아이디 형식: 영문·숫자·`._-` 2~30자 (`isValidId`)
- 입력 필드는 하나. 사용자는 아이디든 이메일이든 같은 칸에 넣는다.
- **제약**: 아이디 계정은 실제 수신 가능한 주소가 아니라 **비밀번호 재설정 메일을 못 받는다**. 실제 학원 계정은 이메일 가입을 권장.

## 회원가입 — 역할별 경로

`POST /api/signup` 하나가 세 역할을 모두 처리한다. IP당 시간당 5회 제한(개발은 100회).

| 역할 | 게이트 | 프로필 생성 시점 |
|---|---|---|
| 학생 | 없음 (이름만 필요) | 가입 즉시 `profiles(role=student)` |
| 강사 | 원장 초대코드(`teacherInviteCode`) **또는** 전역 `INVITE_CODE` | 가입 시엔 안 만듦 → 첫 `POST /api/profile`에서 생성 |
| 원장 | 전역 `INVITE_CODE` + 학원 이름 | 가입 즉시 학원 개설 + `profiles(role=admin)` |

공통: 비밀번호 8자 이상. 이미 가입된 이메일이면 400.

**강사만 프로필 생성이 늦는 이유** — 가입 직후엔 이름·과목·말투가 없어서, 강사 대시보드의 "프로필 저장"이 첫 `profiles` 행을 만든다. 그래서 `role = null`인 과도기 상태가 존재하고, 코드 곳곳에서 이 상태를 별도로 다룬다.

### 학생 가입 시 자동 수강 연결

`enrollToAcademyTeachers()` (`src/lib/account.ts`)가 학원의 **모든 강사 기본반**에 학생을 등록한다. 없으면 "기본반" 강좌를 만들어 붙인다.

이유: 초대 링크 없이 가입한 학생이 `/ask`에서 빈 강사 목록을 보는 것을 막기 위함.

### 초대 코드

`src/lib/invite.ts` — HMAC 서명 코드. `kind`로 용도를 분리한다.

- `kind="t"` — 원장이 강사를 초대 (`/join-teacher/<code>`). 이 경로로 가입하면 전역 `INVITE_CODE` 없이도 되고, 그 학원 소속으로 자동 배정.
- `kind="s"` — 강사가 학생을 초대 (`/join/<code>`). 가입과 동시에 그 강사의 기본반에 수강 연결.

## 로그인 흐름

```
사용자 입력(아이디|이메일 + 비번)
  → toEmail()로 이메일화
  → supabase.auth.signInWithPassword()
  → GET /api/profile 로 서버의 실제 role 조회
  → homeFor(role) 로 이동
```

**핵심**: 착지 화면은 로그인 탭에서 뭘 골랐는지와 **무관**하다. 학생이 "강사" 탭으로 로그인해도 `/ask`로 간다. (`src/app/login/page.tsx`의 `fetchRole()` → `homeFor()`)

`homeFor()` (`src/lib/role.ts`):

| role | 착지 |
|---|---|
| `admin` | `/admin` |
| `student` | `/ask` |
| `teacher` 또는 `null` | `/teacher` |

`null`을 `/teacher`로 보내는 이유: 학생·원장은 가입 시 프로필이 만들어지므로, 프로필 없는 계정은 사실상 강사 가입 직후 상태다.

## 접근 제어 — 2단 방어

### 1단: 서버 (실질 방어)

`src/lib/auth.ts`:

```ts
const gate = await requireRole(req, "teacher");
if ("res" in gate) return gate.res;   // 401/403 응답
const uid = gate.uid;
```

- `userFromRequest(req)` — 토큰만 검증, 역할은 안 봄. **공개/공용 라우트 전용**
- `userWithRole(req)` — uid + `profiles.role` 조회
- `requireRole(req, role, { allowNoProfile })` — 역할 게이트. `allowNoProfile`은 강사 가입 직후 role=null을 통과시킬 때만

> `teacherFromRequest`는 이름과 달리 **역할 검사를 하지 않는다** (`userFromRequest`의 별칭). 옛 호출부 호환용이므로 새 코드에서는 쓰지 말 것.

라우트별 요구 역할:

| 라우트 | 요구 |
|---|---|
| `documents`, `documents/events`, `upload`, `insights`, `invite`, `students`, `quiz/generate` | 강사 |
| `courses` POST·DELETE, GET(내 강좌) | 강사 |
| `courses` GET `?teacher=` | 공개 |
| `admin` GET·PATCH | 원장 |
| `profile` POST | 강사 이거나 프로필 없음 |
| `ask`, `feedback`, `quiz`, `quiz/attempt`, `related`, `popular`, `teachers`, `inquiry` | 공개 (로그인 시 기능 추가) |
| `conversations` | 로그인 (내부에서 role로 분기) |

소유권은 역할과 별개로 쿼리의 `eq("teacher_id", uid)` / `eq("student_id", uid)` 필터가 강제한다.

### 2단: 클라이언트 (UX)

`src/lib/role.ts`의 `useRole(session)` + `src/components/RoleGuard.tsx`:

```tsx
if (!ready) return <RoleLoading />;
if (!session) return <NeedLogin as="teacher" />;
if (role === undefined) return <RoleLoading />;      // 조회 중 — 대시보드 렌더 금지
if (role !== "teacher") return <WrongRole need="teacher" role={role} />;
```

역할 조회가 끝나기 전에는 대시보드를 그리지 않는다 (잘못된 역할에게 UI가 잠깐이라도 보이는 것 방지). 화면 가드는 안내용이고, 실제 차단은 항상 서버가 한다.

## 비밀번호 재설정

`/reset` 한 페이지가 두 단계를 처리한다.

1. 이메일 입력 → `supabase.auth.resetPasswordForEmail(email, { redirectTo: <origin>/reset })`
2. 메일 링크로 재진입 → URL 해시의 recovery 토큰을 supabase-js가 세션으로 교환 → `supabase.auth.updateUser({ password })`

`PASSWORD_RECOVERY` 이벤트 또는 해시의 `type=recovery`로 2단계를 감지한다.

## 알려진 제약

- **아이디 계정은 재설정 메일 수신 불가** (위 참조)
- **Supabase는 비밀번호 최소 길이를 계정 "수정"에만 강제**한다. 관리자 API의 계정 "생성"은 짧은 비밀번호를 통과시킨다 → 데모 계정(`test`/`test`)이 가능한 이유. `scripts/seed-accounts.ts`가 이 차이를 이용해 계정 이관 방식으로 처리한다.
- rate limit이 **인메모리**라 서버리스 다중 인스턴스에서는 인스턴스마다 별도 카운트다. 실제 상한은 설정값 × 인스턴스 수.
- 데모 계정(`test`/`test`, `st`/`st`)은 공개 배포에서 누구나 로그인 가능하다. 시연 후 `npx tsx scripts/seed-accounts.ts --remove`로 정리할 것.
